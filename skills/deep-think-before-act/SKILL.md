# 深度思考先行工作流

## 核心原则

**想三遍，干一次。** 深度思考的时间不会浪费——它省掉了试错的時間。

## 执行步骤

### Step 1: 问题拆解（30秒）
- **目标是什么？** 用一句话说清楚用户真正要什么
- **输入是什么？** 我手里有什么（URL、文件、数据）
- **输出是什么？** 最终交付物长什么样

### Step 2: 路径推演（60秒）
列出3条可能的实现路径，每条写清楚：
1. 做什么（操作步骤）
2. 依赖什么（工具/权限/网络）
3. 可能在哪卡住（已知坑点）
4. 备选方案是什么（这条路死了怎么办）

### Step 3: 选最优路径（20秒）
对比3条路径，选**成功率最高**而非"看起来最快"的那条。
评判标准：有成功先例 > 理论上可行 > 值得一试

### Step 4: 快速验证假设（关键！）
在执行主任务前，先用最小成本验证核心假设：
- 依赖的工具是否可用？→ `which xxx`
- 网络是否通？→ `curl -I` 看状态码
- 权限是否够？→ `ls -la` / `stat`
- 数据格式对不对？→ `head -c 100` 看文件头

### Step 5: 执行（一次过）
按验证通过的方案执行，过程中：
- 每一步检查结果是否符合预期
- 出问题立刻止损，不硬撑
- 记录新的坑点，后续补入skill

## 具体应用模板

### 从URL获取资源类任务
```
目标：下载XXX
输入：[用户给的URL]
输出：文件部署到公网

路径A：yt-dlp 
  - 操作：yt-dlp URL
  - 依赖：yt-dlp已安装、B站网络可达
  - 坑点：B站反爬412
  - 验证：yt-dlp --version && curl -I URL
  优先级：最高成功率

路径B：B站API + Akamai
  - 操作：拿avid/cid → API取backupUrl → curl下载 → ffmpeg合并
  - 依赖：curl、ffmpeg、B站API可达
  - 坑点：API有频率限制、URL有时效
  - 验证：curl API看code=0
  优先级：有成功先例

路径C：浏览器fetch中转
  - 操作：浏览器fetch视频 → base64分块 → 服务器拼接
  - 依赖：浏览器在线、数据量<10MB
  - 坑点：CORS、数据太大传不了
  - 验证：先拿blob.size看大小
  优先级：兜底方案

结论：选路径B
验证：curl API → code=0 ✓
执行：...
```

### 部署类任务
```
目标：部署XXX到公网
输出：http://公网IP/xxx

路径：Nginx容器静态服务
  - /root/public/已挂载到Nginx 80端口
  - 文件放进去就自动可访问
  - 验证：ls /root/public/ && curl localhost/xxx
```

### 代码开发类任务
```
目标：实现XXX功能
输入：需求描述
输出：可运行的代码

路径：
1. 先理解需求，拆解成模块
2. 检查环境（语言版本、依赖包）
3. 写最小可运行原型
4. 验证核心逻辑
5. 逐步完善
```

## 避坑提醒

- **别被"捷径"诱惑**：看起来最快的路往往坑最多（比如yt-dlp）
- **验证要小成本**：先verify再full-go，不要一上来就下6MB文件
- **执行中发现问题**：停下来重新思考，不要"都走到这一步了硬着头皮继续"
- **完成后再优化**：先跑通再优化，不要一次追求完美

## 实际案例复盘

**B站下载任务（用时30分钟 vs 如果深度思考只需5分钟）：**
```
错误模式：直接上yt-dlp（30秒）→ 412（浪费2分钟）
→ 换you-get（30秒）→ JSON error（浪费2分钟）
→ 服务器curl直连（30秒）→ SSL error（浪费2分钟）
→ 代理下载（30秒）→ 超时（浪费2分钟）
→ 浏览器fetch→POST（30秒）→ CORS（浪费2分钟）
→ 分块base64（30秒）→ 数据太大传不动（浪费5分钟）
→ TCP socket（30秒）→ 跨域（浪费2分钟）
→ sendBeacon（30秒）→ 跨域（浪费2分钟）
→ ...最终才想到B站API

正确模式：
想：B站视频下载有哪几种方式？
  - yt-dlp → 上次就412了，这次大概率也一样
  - 浏览器中转 → 有CORS问题，数据要分块太麻烦
  - B站官方API → 有成功先例（第26集）→ 选这个！
验：curl API → code=0 ✓
干：一次过！5分钟搞定。
```
